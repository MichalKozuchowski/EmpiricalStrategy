## Join types and merge logic
- **Inner join**: keeps only rows with matching keys in both tables (e.g. SKU 3 in the left
  table only gets dropped if it has no match on the right).
- **Left join**: keeps all rows from the left table; unmatched right-side values become null.
- Other types: outer join, right join — each produces a different result set.
- **Key rule, always**: check dimensions before and after a merge. Unexpected growth signals a
  problem (duplicate keys); unexpected shrinkage means rows are silently being dropped.

## 1:N, N:1, N:N merges
- **1:N**: one row on the left maps to multiple rows on the right (e.g. a customer merged to
  their orders — the customer's row appears once per order). Result grows — expected and often
  intentional.
- **N:N**: both tables have repeated keys → Cartesian product of all matching combinations, can
  cause explosive growth (the "Bob"/"Robert" duplicate-key example from the slides: 6 rows
  becomes 7+).
- Quick duplicate check: compare the count of unique key values against the table's row count.
- Fuzzy string matching can help automate reconciling near-duplicate key variants
  (e.g. "Bob" vs. "Robert").
- Merging on many columns increases complexity fast — merging on ~10 columns at once can crash
  a system.

## Pandas vs. Dask for large data
- **Pandas**: most readable, most AI-friendly, fine under roughly 10 million rows. Fails outright
  on data larger than available RAM (live demo: a ~5GB file crashed against a 4GB RAM limit).
- **Dask**: same syntax as pandas, but chunks computation to handle big data.
  - **Lazy evaluation**: builds a full plan before executing anything, unlike pandas which runs
    line-by-line immediately.
  - Runs chunks in parallel across CPU cores.
  - Fast for simple aggregates like averages; still slow for quantiles (e.g. a 63rd-percentile
    calculation needs a full data shuffle across all chunks).
  - Live demo: computed average spend by category across 50M rows using only ~0.5GB RAM.

## DuckDB and Polars
- **DuckDB**: SQL inside Python, extremely fast on large datasets.
  - Demo: 300GB of airline schedule data (OAG) — computed route/airline frequency in
    **13 seconds**; pandas failed to complete the equivalent at all.
  - Handles multi-key joins (e.g. color ID + SKU + state + zip + date) that pandas chokes on.
  - Syntax example: `SELECT name, SUM(spend) AS total_spend FROM df GROUP BY name ORDER BY total_spend DESC`
- **Polars**: fast pandas alternative, similar syntax; recommended over pandas where practical.
- Performance ordering (simple merge): pandas slowest; DuckDB and Polars both significantly
  faster, with the gap widening past ~10M rows.

## What we actually built in this live session (with Claude)
Working through the same taxi+ACS merge live, step by step:
1. Merged 2024 Chicago taxi trips (9,793,842 rows) to ACS median household income by tract
   (Illinois-filtered ACS, 3,123 tracts) — clean n:1 merge, row count unchanged after merge
   (shape-check habit confirmed no duplicate-key blowup). ~31.6% of trips matched to an income
   value; unmatched rows were mostly missing `Pickup Census Tract` in the raw data, plus at
   least one real gap (Census Tract 9800 = O'Hare Airport, negligible residential population).
2. **Average raw fare vs. tract median income**: correlation ≈ **-0.007** — essentially zero.
   Raw fare is dominated by trip distance, which swamps any income effect.
3. **Fare per mile vs. tract median income** (controlling for distance, winsorized at 99.5th
   pct): correlation rose to **0.155** — a real, modest positive relationship once distance is
   controlled for.
4. **Same fare-per-mile analysis, restricted to tracts with ≥10 trips** (to avoid noisy small-
   sample tract averages): correlation strengthened to **0.268** — dropping noisy low-count
   tracts made the income relationship clearer, not weaker, suggesting it's a real pattern.
5. **Tip % of fare vs. tract median income** (in progress at end of session) — restricted to
   credit-card payments only, since Chicago taxi data does **not** reliably record cash tips
   (they typically show as $0 regardless of actual tip), which could otherwise bias the result
   by a tract's cash-vs-card payment mix rather than true tipping behavior. Expect this to land
   near the class's reported **R ≈ 0.6** once run — worth checking the actual output against
   that figure directly.
